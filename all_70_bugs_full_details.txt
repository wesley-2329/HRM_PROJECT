5. Cross-cutting engineering requirements
Inspect the existing repository, package manager, framework, routes, API client, auth/session mechanism, schemas/models and current tests before editing. Do not assume a framework or rewrite the app.
Trace each defect through UI → state/form handler → API request → backend validation/business logic → database/storage → returned response → UI refresh. Fix the root cause, not just the visible symptom.
For all create/update actions: one click must issue one logical mutation; disable while pending; make retries safe; do not show success until persistence succeeds; preserve user input on failure; refresh from canonical server data.
For duplicate/data-loss issues: inspect create vs update/upsert logic, state replacement vs append/merge, unique constraints, retries, double-clicks, and idempotency. Add regression tests with two sequential records and repeated submissions.
For auth/RBAC: use the authenticated identity and server-side permission checks. Never rely on hiding UI controls as the only authorization. Do not mask 401/403 errors by silently displaying stale/mock data.
For uploads/downloads/exports/PDFs: validate real bytes, response MIME type, filename, file size/type, storage path and permissions. A success message must correspond to a valid artifact that can be opened/downloaded.
For date/time: define a consistent ISO 8601 timestamp/timezone policy, validate at API boundaries, and test persisted values after reload. Do not store bare time strings where a date-time is required.
For UI: use responsive layout constraints, stable table column sizing, accessible contrast, visible loading/empty/error states, correct dropdown hover boundaries, and global toast/dialog layers not clipped by parent containers.
Do not hardcode fake success, sample data, or mock fallback as if it were live. If backend capability is missing, report the blocker instead of faking it.
Add unit/integration tests for each fix and a browser-level smoke test for the user flow. Run lint/typecheck/build/test commands available in the repo and report actual results.
Keep unrelated behavior unchanged. Do not remove existing features, change route contracts, modify secrets, or perform destructive database migrations without a clear plan and approval.
